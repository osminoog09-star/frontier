# 🌐 FRONTIER — Сеть и глобальный мир

> Цель: играть через интернет, сохраняться в облаке, кооп с другом, а в перспективе —
> **глобальный персистентный мир** с множеством игроков. Это после ALPHA; здесь — план и архитектура.

## Этапность
1. **Облачные сохранения** (Неделя 3): одиночная игра, но сейв колонии хранится на сервере.
2. **Кооп на двоих** (Неделя 4 = ALPHA): общая карта, авторитетный сервер.
3. **Глобальный мир** (после месяца): общий персистентный сервер, много колоний.

## Модель кооперации (выбор дизайна)
- **Вариант A — Общая колония:** оба игрока управляют одними и теми же пешками/постройками (как в коопе Factorio).
  Проще для друзей, меньше сущностей. *Рекомендуется для первой ALPHA.*
- **Вариант B — Соседние колонии:** у каждого своя колония на одной карте, можно помогать/торговать/воевать.
  Ближе к «глобальному миру», но сложнее.
- Решение: **Alpha = Вариант A** (общая колония), затем эволюция к B и к глобальному миру.

## Сетевая топология
- **Авторитетный сервер** (anti-cheat, единая истина). Клиенты — «тонкие»: шлют команды, рисуют состояние.
- Транспорт: **WebSocket** (через `ws` на Node). Низкая задержка, простая интеграция в браузер.

## Синхронизация
- **Модель: команды → серверный тик → снапшоты/дельты.**
  1. Клиент формирует команды (`place_build`, `set_priority`, `mark_tile`, `attack`…), шлёт серверу.
  2. Сервер применяет команды в начале тика, прогоняет детерминированную симуляцию.
  3. Сервер рассылает периодический снапшот + дельты (что изменилось).
  4. Клиент применяет, делает интерполяцию/сглаживание движения пешек.
- **Клиентское предсказание** для отзывчивости камеры/выбора (симуляция — на сервере).
- *Зачем детерминизм (Неделя 3):* меньше трафика (можно слать только команды + редкие снапшоты для коррекции),
  воспроизводимость, проще дебаг.

## Серверная архитектура
```
Client (browser, render+input)  ── WebSocket ──►  Game Server (Node + ws)
                                               │   ├─ Rooms (комнаты/миры в памяти)
                                               │   ├─ Sim tick loop (авторитет)
                                               │   └─ Persistence (SQLite → Postgres)
```
- **Комната** = один мир/колония: состояние, список игроков, цикл тиков.
- **Персист:** автосейв состояния комнаты в БД; «продолжить» загружает.
- **Идентичность:** device-id (Неделя 3) → опц. аккаунт (ник+код/ссылка для друга).

## Глобальный персистентный мир (видение, после месяца)
- Один большой общий мир, разбитый на **регионы/шарды** (каждый шард — отдельный процесс/комната).
- У каждого игрока **своя колония** в регионе; мир живёт, даже когда игрок оффлайн (ограниченная симуляция/«заморозка»).
- **Взаимодействие:** караваны и торговля между колониями реальных игроков, совместная оборона от PvE-набегов,
  опциональные конфликты (PvP-зоны).
- Масштаб: горизонтальное масштабирование по шардам; матчмейкинг по регионам; БД Postgres.
- Античит: сервер-авторитет, валидация команд, rate-limit.

## Технологический стек (рекомендация)
- **Сервер:** Node.js + `ws` (или фреймворк `Colyseus` — даёт комнаты/синхронизацию «из коробки»; рассмотреть на Неделе 3).
- **БД:** SQLite (dev/alpha) → PostgreSQL (масштаб).
- **Хостинг:** VPS + Docker; для альфы хватит одного дешёвого инстанса.
- **Клиент:** тот же браузерный код; добавляется `net.js`. Оффлайн-режим сохраняется.

## Требования к коду для сети (готовим заранее)
- Симуляция без обращений к DOM/Canvas (разделение — см. ARCHITECTURE.md).
- Детерминизм: сид RNG в состоянии, ввод как команды, фикс. шаг.
- Сериализуемое полное состояние (есть в save v2) + дельта-сериализация (Неделя 4).

## Риски и решения
- *Рассинхрон:* периодические снапшоты-коррекции + хеш состояния для проверки.
- *Задержка:* клиентское предсказание камеры/UI, интерполяция движения.
- *Читеры:* только сервер меняет мир; клиент не доверенный.
- *Стоимость:* начинаем с одного VPS, шардинг по мере роста.
